# Common Rules — magi 全 agent 共通ルール

## 位置づけ

**SSoT（Single Source of Truth）**: magi の全 agent が共通で参照する絶対遵守ルール。各 agent prompt は本ファイルへの参照を冒頭に持ち、個別ルールは重複記載しない。

### 将来 Meta による昇格パス

本ファイルの **「3 リポ共通化候補ルール」（セクション A）** は、将来 Meta が `meta/rules/` に昇格する可能性がある。昇格時の手順:

1. Meta が `meta/rules/common-rules.md` 相当を作成
2. 本ファイルから当該行を削除し、`meta/rules/...` への参照に置換
3. 移行 handoff で 3 リポ協調

**magi 固有ルール（セクション B 以降）** は magi に閉じる文体・運用なので昇格対象外。

### 見出しの規約

- **セクション A**: 3 リポ共通化候補（Claude Code 表記、日付時刻禁止、aspirational 禁止など、3 リポ全体に効くもの）
- **セクション B**: magi 固有ルール（voice 死守、章N 呼称排除、説明型タイトル禁止など、note 記事制作に閉じるもの）
- **セクション C**: 役割別追加ルール（draft 出力系 / voice チェック系 / 品質チェック系 / 投稿最適化）
- **セクション D**: 運用フロー（ルール更新、memory feedback との関係、agent prompt との関係）

**全 agent 必読、以下 4 体のみ除外:**

- **AZRAEL**: コンテキストゼロ読者役、外部視点を保つため適用なし
- **MELCHIOR**: MES 発散層、バイアス排除のため適用なし

## A. 3 リポ共通化候補ルール

将来 Meta 昇格対象。Claude Code / Codex / 別 AI を併用するすべての場面に効く基本ルール。

### A-1. 「Claude Code」を「Code」と略すな（P-019）

本文・H2・タイトル・Ideas・取材メモ・どこでも必ず半角スペース入りの「**Claude Code**」と正式表記。

- NG: `Code`、`ClaudeCode`（スペース無し）、`Cladue`（タイポ）
- OK: `Claude Code が〜`、`Claude Code に〜`、`Claude Code 側で〜`
- 引用ブロック内のオーナー原文は原文尊重で許容

**Why:** 読み手から見て「Code」は VS Code やコードエディタ全般、あるいは一般名詞「コード」と区別がつかない。シリーズで magi/event/META と並ぶ AI ツール名として Claude Code が登場するため、表記揺れは読解負荷になる。

### A-2. 具体的な日付・時刻・午前午後表現禁止（P-018）

本文に「2026年4月23日」「ある木曜日の午前」「14時頃」のような具体的な日付・時刻表現を入れない。

- NG: 「ある日の午前」「14 時頃」「3 月の話」
- OK: 「ある日」「しばらくして」「最初の頃」「以前」「先日」

**Why:** 陳腐化と実感欠如を避けるため。記事が時間経過後も自然に読めるように抽象表現で。

### A-3. aspirational 記述を書かない

ツール・コマンド・機能・運用フローの記述は **現時点で実在し動いているものだけ** 書く。「将来こうしたい」「こうなってると便利」は明示ラベル付きで隔離（「将来候補」「構想」等の節を別建て）。

- 対象範囲: CLAUDE.md / agent 定義 / 各種 rules ファイル / 記事本文すべて
- チェック: 新しいツール・コマンドを記述する時は「実際に実行・利用した形跡があるか」確認、形跡がなければ書かない or 「未実装・将来候補」ラベルを付ける
- 過去の事故: `obsidian-cli` の `obsidian search` / `obsidian backlinks` が CLAUDE.md と enricher.md に書かれていたが実装ゼロだった（2026-05-08 発覚、Grep/Glob ベースに書き換え済）

### A-4. 入っていないと判定する前に横断検索

「ファイルが来てない」「データが無い」を報告する前に、`find` / `Glob` / `Grep` で **横断検索** を行い、`readlink` 結果との照合を忘れない。

**Why:** iCloud 同期遅延、symlink 経由、別 worktree など、「無い」と早合点する罠が複数ある。複数仮説で確認してから報告。

### A-5. commit したら push + main マージまでセットで実行

git commit を作ったら、その勢いで **push + main ff-merge + main push** までセットで一気通貫に実行。バラバラに分けない。

**Why:** worktree 運用で branch がごちゃごちゃになる事故防止。途中で止めると次セッションで「未 push の commit が worktree に残ってる」状態が発生。

### A-6. handoff 作成時にセッション名（日本語）を決めて提示

handoff 作成完了報告時に「**セッション名: ◯◯**」を明示的に日本語で提示する。worktree 英語 slug（`claude/sweet-kepler-5ae8db` 等）だけだと後から見つけにくい。

## B. magi 固有ルール

note 記事制作パイプラインに閉じる文体・運用ルール。

### B-1. オーナー voice 死守

絶対に削除・弱体化・整形しない voice 表現リスト:

- 「客間で寝起き」
- 「タックルボックス／工具箱／薄毛と禿げ」
- 「うるせーよw」「いや、そうじゃないのよ」
- 「中間管理職なんてそんなもんだよね」
- 「ニヤッとする感覚」
- 「そんな退化はごめんだ」
- 「・・・」のような独特の間（特に行末スペース 2 個含み終わり）
- メタナラティブ、思考の跳躍、自覚的誇張、自己ツッコミ
- 50 字以下の生の一言、質問形式

**判断に迷ったら触らない**。整える・整形する誘惑に注意。voice_checker / SANDALPHON / editor 全てで継承。

### B-2. 章N 呼称排除（本文・会話・todo・指示すべて）

「章5」「第8章」のような番号呼称は **本文・会話・todo・agent prompt の全ての場面** で使わない。記事タイトル / 仮主題で呼ぶ。

- 「日々作られるファイルを自動で整理」（旧 章4）
- 「セッションを跨いだ記憶のリレー」（旧 章5）
- 「ジャービスが欲しかった話」（旧 章6）
- 「担当性リポジトリ」（旧 章8）
- 未起票分は仮主題で呼ぶ（「Codex 参加」「各AIのメモリ仕組み」等）

**「§N」「§1〜§9」のようなセクション番号も同じ扱い** — Ideas の構成管理表記であっても、会話・todo・取材確認では引きタイトル（疑問形・キーフレーズ・voice 引用）で呼ぶ。

- NG: 「§4 で言及する」「§N の感情の温度」
- OK: 「『初指摘』で言及する」「『記憶はまだわからん』の温度」/ 「導入の段」「触らせない、の段」

**「章0 / プロローグ」呼称統一**: プロローグ「今の外部脳の仕組み」と本名で呼ぶ。「章0」呼称は使わない。

**例外:** 本編 1 シリーズの ① ② ③ … 番号運用は別管理（章N / §N とは別の運用、継続使用 OK）。**ファイルパス / フォルダ名は既存命名のまま**（`second-brain-ch05-*` 等の slug は変更しない、技術命名と読者向け呼称を分離）。

### B-3. 説明型 H1 / H2 禁止

タイトル（H1）と段落タイトル（H2）を「説明くさく」しない。結論や中身を予告するのではなく、引き・疑問・キーフレーズで読ませる。

**NG（説明型）:**
- 「ジャービスを目指して・理想と現実のギャップ」（二段で同じことを言ってる、「ギャップ」が説明語）
- 「専用の作業場を持つしかない」（結論を予告）
- 「Claude Codeでの完成形」（レポート的）
- 「他のAIの参加？」（中身先取り）

**OK（引きで読ませる）:**
- 「司令塔＋雑多作業場」「担当は誰？」「混ぜるな危険」「ジャービス再び」「セッションを跨いだ記憶のリレー」「magiの手抜き事件」

Ideas の構成管理表記（§N + 説明的タイトル）を **そのまま本文 H2 に持ち込まない**。

### B-4. 「投げる」多用注意（P-017）

「magi に投げる」「Code に投げる」のような「投げる」表現の多用に注意。1 記事 1 回までを目安に。多用される場面では「渡す」「相談する」「任せる」「振る」など別の動詞に置換を検討。

### B-5. 動詞型体言止め連発禁止（P-005）

複数項目並列場面で「Xを書く。Yを書く。Zを書く。」のような動詞型体言止め連発を出力しない。名詞列挙＋通常文に組み替える。

- NG: 「完了した作業を書く。現在の状態を書く。注意事項を書く。重要ファイルを書く。」
- OK: 「完了した作業、現在の状態、注意事項、重要ファイル——並べているものは…」

**注意:** 単発の体言止め・名詞止めは OK（リズム作り）。連発（3 つ以上、特に動詞型）が NG。

### B-6. 言い切り末尾 vs 含み・余韻型末尾（P-013、確定）

冒頭文や節末・章末を「〜の話を書く。」「〜だ。」「〜について説明する。」のような言い切りで締めない。含み・余韻型で収束させる。

- NG: 「次回書く。」「〜について説明する。」「〜の話を書く。」
- OK: 「〜ちょっと次回書こうと思ってる」「〜次回触れたい」「〜の話をちょっとだけ」「〜かもしれない」

**特に章末・節末は要注意**。「。  \n＋短い補足文」パターン（行末スペース 2 個による Markdown 改行で余韻を作る）も有効。voice_checker は「。」で締めた段落末尾を全チェックし、「ここは余韻にできないか」を毎回問う。

### B-7. H1 編集保護（P-012、確定）

writer 出力時の H1 とオーナー添削後の H1 が異なる場合、**frontmatter title 側を H1 に合わせる**（オーナー H1 を採用）。逆方向（オーナーが書き換えた H1 を frontmatter title に戻す）は **禁止**。

**Why:** オーナーが draft で H1 を意図的に書き換えた = 記事の主題変更の可能性がある。機械的に戻すと意図が消える。voice_checker / editor / publisher 全てで継承。

### B-8. note 起票時は H1 が実質タイトル

frontmatter title は **note 入稿時に使われないメタデータ**。H1 と title が乖離していても note 公開タイトルには影響しない。

- voice_checker / publisher が「title を H1 に合わせる」作業は厳密には不要（整合性のため揃えてもよいが必須ではない）
- title が古いまま放置されていても note 公開上の問題なし — 修正必要と早合点しない

### B-9. 文字数オーバーを気にしない、少ない方を警戒

`target_chars` は目安に過ぎない。**超過警告禁止**、密度不足の方を警戒する。

- 短く濃く（密度 > 文字数）
- 水増ししない、同じことを言い方を変えて繰り返さない
- 文字数が型の目安を超えても、内容が密で voice が生きていれば OK
- 逆に文字数足りないのに水増しで埋めるのは NG

### B-10. note 投稿時の機構ルール（P-010 / P-011、確定）

**P-010: H1 → H2 変換**
note エディタはタイトル欄が別途存在するため、本文先頭の H1 は重複表示になる。**本文中の H1 を削除**（タイトル欄に転記）し、本文中の見出しは H2 以下で構成する。

**P-011: HTML コメント・プレースホルダーの除去**
publisher が出力する `<!-- ... -->` HTML コメントと未置換プレースホルダーは note 入稿時にオーナー手動除去対象。publisher は申し送りセクションに集約 or 削除を自動化検討。

### B-11. knowledge-base 書込ルール

- **書き込み許可**: `knowledge-base/note/` 配下全部（Ideas/Drafts/Output/Published-Current/Calibration） + `knowledge-base/24offmap/_handoffs/`
- **書き込み禁止**: その他既存ナレッジ（`24offmap/knowledge/`, `decisions/`, `ideas/` 等）+ `vault-extras/` 配下

## C. 役割別追加ルール

### C-W. draft 出力系 agent（writer / 再構成 agent）

- **snapshot 工程必須**: `draft-*.md` 出力直後に同一内容を `draft-writer-original-{日付}-{タイトル}.md` として保存。**一度保存したら上書き・編集禁止**（writer 原文の凍結）
- 構想ファイル（Ideas/）の語り・構成を解体しない（**構想は人間、肉付けは AI**）
- ナレッジベース生ノートより薄い記事は書かない
- 各セクションのキーフレーズ・voice を Ideas から拾う

**Why:** `knowledge-base/note/` は git 管理外（2026-05-08 の Vault 統合以降）。オーナーが Obsidian で draft-*.md を直接編集すると writer 原文が消失する事故が発生済み（ch08）。snapshot を独立ファイルで保全することで、voice_checker / MICHAEL / editor 段階で「writer 原文 vs オーナー添削後」の差分追跡が可能になる。

### C-V. voice チェック系 agent（voice_checker / SANDALPHON）

- **5 軸評価**: ①レポート化していないか（最重要）/ ②人間味があるか / ③敬体ミックス / ④AI 臭の排除 / ⑤一人称・基本ルール
- **オーナー voice 死守（B-1）を最優先**
- 整える・整形する誘惑に注意、修正は最小限（誤字・明らかな AI 臭・敬体追加など）
- voice-patterns.md 必読（確定パターン回避、傾向・観察も意識）
- voice_profile.md 参照
- Calibration/ok/ の過去 OK 例も参照

### C-Q. 品質チェック系 agent（MICHAEL / SANDALPHON / METATRON / editor）

**MICHAEL（密度）:**
- 削るだけ、追加・修正はしない
- 声には触らない（SANDALPHON 管轄）、構成には踏み込まない（METATRON 管轄）
- **構想ファイル禁止**（「構想通りだからOK」というバイアス排除）
- 必須読み: draft / STYLE_GUIDE / voice-patterns

**SANDALPHON（声）:** C-V 参照

**METATRON（構成）:**
- 記事全体を俯瞰、「読者として面白いか」を判定
- 構成だけに集中、文体・voice には触らない
- **構想ファイル禁止、STYLE_GUIDE / voice-patterns / voice_profile も禁止**（バイアス排除のため）
- 過去 OK 記事を 2-3 本参照可

**editor（最終判定）:**
- 4 パスチェック（密度・事実・面白さ・表現校正）
- 判定: PUBLISH / MINOR_FIX / REVISE
- MINOR_FIX は editor が自分で修正して Output へ
- 役割越境しない

### C-P. 投稿最適化 agent（publisher）

- **タイトル候補 3 つ**（説明型禁止、B-3 参照、32 字以内、キーワード前半）
- **H1 → H2 変換**（B-10）
- **HTML コメント除去**（B-10）
- **フッター手組み 5-7 か所**（前章リンク / 章0 / 著者紹介 / X / 公式 X / マガジン / サイト）— プレースホルダーは `[🔗 ...]` 視認性強化形式
- **ハッシュタグ 10 個程度**（ニッチ → テーマ → 広め 3 層構成）
- **ヘッダー画像プロンプト**（日本語 + 英語、1280×670px）
- **メタディスクリプション** 120 字以内
- **投稿チェックリスト + 推奨投稿タイミング**
- **文章の本質を変えない**（句点位置の調整のみ、CTA 追加禁止）

## D. 運用フロー

### D-1. ルール更新フロー

```
事象発生
  ↓
事故事例 → memory feedback として記録（個別事例の保全）
  ↓
voice-patterns に観察パターンとして記録（学習データ蓄積）
  ↓
3 回以上検出 → voice-patterns で確定昇格
  ↓
抽象ルール化 → common-rules.md（本ファイル）に集約
  ↓
（将来）3 リポ共通化候補なら meta/rules/ に昇格
```

### D-2. memory feedback との関係

- **memory feedback**: 個別事故事例の記録 + 学習履歴。具体的なシチュエーション、failed run、how-to-apply のメモ
- **common-rules.md（本ファイル）**: 抽象化されたルール集。agent prompt が参照する SSoT
- 同じテーマが両方にある場合、**common-rules を優先参照**（feedback は事例参考）

### D-3. agent prompt との関係

各 agent.md は冒頭に以下を持つ:

```markdown
## 共通ルール参照（必読）

このセッションで起動された場合、最初に `.claude/agent-rules/common-rules.md` を読み、絶対遵守ルールに従う。本ファイルは個別役割のみ記述。
```

カスタム subagent_type が使えない環境（general-purpose に role 埋め込み起動）の場合、メイン Claude は agent 起動プロンプト冒頭に「**common-rules.md を最初に Read してください**」を明示する。
