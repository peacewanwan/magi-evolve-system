## 【劣化した脳をAIで補完】なぜ情報共有にこだわるのか

前章で「セッションが切れても話が繋がる仕掛け」の話を書いた。要は引き継ぎファイルを残す仕組みなんだけど、書いてる途中で、自分が前から欲しかった何かにちょっと近づいてる気がしてきた。

それを言葉にすると、いやちょっと大げさだなと思う。アイアンマンのジャービスみたいなのが欲しかった、という話だから。

---

## アイアンマンのジャービス

アイアンマンに出てくるジャービス（J.A.R.V.I.S.）をご存じの方、ご存じない方も、色んなSF映画に出てくるAIと人間の対話を思い出してほしいんだけど、人間側がいちいち用途や作業別を意識してAIに話しかけてることなんてないと思う。

トニー・スタークが「ジャービス、これ調べて」「ジャービス、設計図出して」「ジャービス、今日の予定は？」と話しかけるとき、いちいち「これは検索担当のAI」「これは設計担当のAI」「これはスケジュール担当のAI」と切り替えてない。一人のジャービスが全部知ってる前提で会話が進んでいる。

主人の話を全部聞いてる。文脈も覚えてる。何の作業をどこまで進めたかも分かってる。話しかける側は中身の構造を意識しなくていい。

これ、フィクションだから当たり前なんだけど、AIを実際に使ってみるとこの「当たり前」が現実には全然成立してないことに気づく。

ちなみに、以前「Magiについて」を書いたときも一度だけSF映画のパーソナルAIの話に触れている。あのときは Magi 単体の話だった。今回はもうちょっと広い範囲、つまり自分が触ってる AI 全部の話。

[🔗 過去記事『Magiについて』のリンクをここに貼る]

## 機能ごとの使い分け

自分の手元には、AI が動いている場所がいくつかある。

note を書くための magi。Web サービスを開発するための event。あとから司令塔として加わる META。それぞれ別のリポジトリ（作業場）として独立していて、別々の文脈・別々のメモリ・別々の設定で動いていた。プロローグで書いた通り、この Claude Code 以外にも他の LLM を随時利用している。

なんでこんなことになってるかというと、Claude Code というツールは、リポジトリ単位で機能を分けた方が運用上扱いやすい構造になっているから。一つのリポジトリに全部詰め込むより、目的ごとに分けた方が、設定もメモリもファイル管理もシンプルになるから。

ただ利用者の自分から見ると、これ全部「自分の AI」なんだよね。note 用とサービス用で別人格を相手にしてるつもりはなくて、自分が話しかけてる先は同じ「自分の AI」だと思っている。
というか思いたい。

なのに作業するたびに、「今は magi」「これは event」と意識しないといけない。指示の出し方も微妙に変わる。「magi はこういう仕様だから」「event はこの設定だから」を頭の中で切り替える。これはイマイチ未来感が薄れる。本来なら、Magi とか event とかリポジトリ単位ではなく Claude Code 全体を「ジャービス」みたいな名前で呼びたい。

## 並行作業による混乱

しばらくこの体制で動いていると、もう少し具体的なめんどくささが見えてきた。

たとえばだけど、何かのテーマでだいぶ前に AI と壁打ちをした記憶がある。で、いざその続きをやろうとしたとき、「あれ、この前この壁打ちしたのって magi だっけ event だっけ？」となる。

magi の方を開いて違うっぽいことに気づき、event の方を開いて違うっぽいことに気づき、結局どっちでもなかったらしくて「あれ、別の壁打ちと混ざってる？」となる。

これ、AI 自身の機能差の話じゃなくて、自分が前にどこで何を話したかを覚えていないといけない、という話。AI に文脈を持たせるのが大変というより、**自分が AI 同士の連絡係をやらされている**みたいな状態。

たぶんこういう人が他にもいる気がする。

これ、いくつか前の note でも同じ違和感を書いた気がする。あのときは Magi の中だけで完結する話として書いてたけど、結局は magi の外まで広がる話だった、ということが後から分かってきた。

[🔗 過去記事『Magiについて』のリンクをここに貼る]

機能を意識すること自体が面倒、って、なんか贅沢な悩みに聞こえるかもしれない。ただ AI に指示を出す側として考えた場合に、指示を出す前の段取り（「これはどっちでやる？」「あれは前にどこで話した？」）が増えるのは単純に効率的じゃない。相棒感も薄まる。

## やっぱりジャービスが欲しい

結論から言うと、リポが違おうと、極論 LLM が違おうと、自分が使ってる AI は全部「自分仕様で共通」であってほしい、と思う。

要するにジャービスっぽくしたい。

機能で分かれていることを意識しないで済む。話しかける側は「今これはジャービス」「今は別のジャービス」と切り替えない。一人だけ知っていれば足りる。

まあ書きながら自分でも、ちょっと厨二的なわがままだなとは思う。人によっては「リポごとに切り替わってる方が分かりやすい」って人もいると思う。

ただ自分の場合は、AI は使い手が使い分ける道具ではなく、使い手が用途を意識しなくても使える相棒であって欲しい。

## 果たしてジャービスの構造は？

いや、待てよ。ジャービスが欲しい欲しいと言ったところで、ジャービスって実際はどういう仕組みで成立してるんだろう。

映画の中では一人格に見える。ただ実装上の話としては、たぶん裏側で何らかの仕組みが動いて文脈を共有しているはず。一個の AI が全部知ってるのではなくて、複数のサブシステムが何かしらの方法で繋がっていて、利用者から見た時に「分かれて見えない」ように作ってある、というのが現実的な作り方だと思う。スタークインダストリーズの事だから量子コンピューター上で動いている全く概念の違うものの可能性の方が高い気もするけど。

SFの話は置いておいて、現実的な運用上の落とし所としては「中身がほんとに一人格か」ではなくて、「**利用者から見て分かれていないように見えるか**」の方。これは構造の話というより、UI とか UX 寄りの話に近い。中身がどれだけ複雑でも、表に出てくる体験が一人格に見えればそれでいい、ということになる。

自分の AI 環境に置き換えると、入口が magi と event に分かれていても、文脈さえ共有できていれば、利用者から見れば「分かれてないように見える」状態は成立する。実際に前回作った仕組みは、結果としてそういう方向に寄せていく装置として機能していた、と後から見て思う。

ちなみに Claude を作っている Anthropic は、Project ごとに会話やメモリを隔離する設計を取っているらしい。会話の中身が別の Project に漏れない、というのを安全側の前提として置いている。エンタープライズで AI を使う前提だとそりゃそうだろうな、と思う。

ただ個人で AI を横断してシームレスに使いたい自分の用途には、ちょっと合わなかった、というだけの話。

## あと少しで・・・

ここで前回の話に戻る。

前章で書いた handoff の仕組みは、もともと「セッションが切れても話が繋がるようにしたい」という、極めて地味な動機で作った。タスクが消える、文脈が消える、ということに地味に困っていたから、その場しのぎの解決として AI に渡したい情報をファイルに残しておく、というのを始めた。最初の頃は本当に1セッション内の便利機能みたいな扱いで、思想とかこだわりとかとは全然関係なかった。

それが、複数リポで使うようになって、別々のリポの間でも引き継ぎファイルを共有できる構造に進化した。Claude Code 側いわく、リポの境界を跨いで同じ「自分の AI」が文脈を持ってる状態が作れている、ということらしい。

それで、書いてる途中でハッと気がついた。

これ、前に書いた「自分仕様で共通の AI」に近づいてきてる気がする。

handoff という仕組みを作っているとき、自分は別にジャービスを目指していたわけじゃなかった。タスクが消える問題を解きたかっただけ。指示の出し直しが面倒だっただけ。ただ、結果として出てきたものは、SF 映画のパーソナル AI に少し近づいた構造だった。

仕組みを先に作って、後から「あ、これってそういうことだったのか」と理想が見えてきた。これはゴールを決めてから設計したわけじゃないので、自分でも面白いなと思う。「やりたかったのはこれ」と最初から明確に言語化できていたわけではなくて、目の前の不便を一つずつ潰していったら、後から振り返ってみて「あれ、これSFに出てくるAIに近い形してない？」となった、というのが正直なところ。

完成形を最初に描けるなら、それはそれですごいんだけど、自分の場合はそんなに賢くない。動かしながら、ちょっとずつ意味が後追いで見えてくる方が多い。

## 作業環境に依存しない

実際に使い始めてから、気づいたら一個の習慣が消えていた。

「あの前の話、覚えてる？」みたいな確認を、AI にあまりやらなくなった。

以前は新しいセッションを開くたびに、前回どこまで話したか、何の文脈で動いてたかを軽く説明し直していた。それが、いつのまにか説明し直さなくても会話が成立するようになっている。AI 側が引き継ぎファイルを勝手に拾って、前提を持った状態から話が始まるから。

これは別のリポを開いた時も同じで。magi から event に移動しても、前提のリセットが起きない。「event 側だから一から説明しないと」が要らない。話が通じなかったら、「ちょっとログ確認して」と言えばリポを跨いで過去ログを確認して、大抵求めた答えが出てくる。「自分の AI」と話している感覚に近い。

## 現実の壁

ここまで読むと、handoff の仕組みを作ったらジャービス完成、めでたしめでたし、みたいな話に見えるかもしれない。

ただ、現実はそんなにすっきり終わらなかった。

仕組みは動いている。リポ間で文脈は共有されている。それ自体は問題ない。問題は、その仕組みを動かす上で **新しい悩みが出てきた**こと。

たとえば、Obsidian の運用方法を整える作業をしているとする。最初は magi の使い勝手を改善する話だったから magi 側でやっていた。ところが進んでいくうちに、それが event 側にも関係してくる話だと分かってくる。さらに進むと、magi と event を跨いで情報を共有するための作業に変わってくる。

そうなると、前段の「機能ごとの使い分け」でも書いた通り「**この作業、どっちのリポでやればいいんだ？**」となる。

magi でやっていいのか、event 側に移すべきなのか、それともそもそもどっちでもない方がいいのか。「機能で意識したくない」と言ってたはずなのに、結局「どの機能で動かすか」を意識して悩んでいる。思想と現実が、もう一段細かい次元で食い違っている感じ。

しかもこの手の「どっちでやる？」案件、今後も増えてくる予感があった。note と Web サービス両方に関わる作業もあるし、どっちでもない、AI まわりの工夫そのものを試したい時もある。そのたびに「これは magi 寄り？ event 寄り？」を判定するのは、「magi だっけ event だっけ？」の悩みと地続きで、構造としては全然解決してない。

ジャービスを目指して仕組みを作ったら、ジャービスを動かす場所をどこにするかで悩み始めた。書いてる本人としては「結局どこかで悩むんかい」という気分にはなった。

この悩みをどう解いたかは、また次に書こうと思う。仕組みで解決した方法があって、それがまた書きながら自分でも「あれ、なんでこれ最初から思いつかなかったんだろう」という、ちょっと間抜けな話になる気がする。
