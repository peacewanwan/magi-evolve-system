ディスクを 64GB 食われた。それでも、そいつを抜かなかった。これはその後どうなったかの記録になる。

以前Codex を入れた事によるトラブルの話を書いた。
[🔗 失敗01『AIが暴走したっぽいのでAIに捜査させたら犯人が特定できた』のリンクをここに貼る]

当時の記事ではCodexを入れた経緯については軽くしか書いてなかったけど今回はそのCodexについて少し書いてみようと思う。


そもそもCodexに手を出したのは単純に「Claude Codeと同じような事ができるAgent系AIがOpenAIから出たから」。Chat GPTでフロントランナーだったOpenAI、今でも世間一般では「ChatGPT」がAIの代名詞みたいになってるけど、一般人のアーリーアダプターやAIを本格的に活用している界隈ではすっかりClaude（Claude Code)がトレンドになっている。そんな中、満を持して登場してきたCoding用AIエージェント。一応なんちゃってバイブコーディングをやっている意識低い系おじさんとしても、何ができるのか？ どんな差があるのか？ 興味があるのでとりあえず入れてみた、て言うのが最初の動機。

## まずは安全策

Claude Code は普通に動いてるし、レビューも自分でやってもらってた。さて Codex には何をしてもらおう・・・
できれば、これも自分の理想に合わせて「一つのAI」の中に組み入れたい

ただ、Claude Code がもう回している仕組みの中に、別の AI を直接組み込むのは怖かった。何ができて何をするかわからん相手と、いきなり同じ部屋に住ませる気にはなれない。
まぁ、結果として例の事件を起こしたわけだけど・・・

## Codexの役割

そこで Codex にやらせたのは、リポジトリを読むことだけ。直接スクリプトを編集させるのは無し。Claude Code が回している作業に、いきなり手を突っ込ませはしない。読めるところまでは見せる、でも書くのは無し。そこだけは最初に決めた。

明確な目的があって入れたわけじゃない。今動いている仕組みにいきなり組み込むのは不安だったので、まずは第三者の目として使ってみよう、くらいの感覚。

普通、ツールを入れるときは「このツールにこの仕事をさせる」って決めて入れる人が多いと思う、て言うかそうするべきだと思う。ただ、AI に関してはまだまだ新しいツールということでまだまだ明確な目的は無しで使い始める人も多いと思う。今回もその感じ。

今までClaude Code中心というかClaude Codeのみでプロジェクトを進めていてプロセスも結果も全てClaude Codeを信じてやってきた。というか信じてやるしかなかった。

そこで、医療でいう「セカンドオピニオン」的な使い方でCodexを使うことにした。Claude Codeがおかしな事やってればそれを暴いて教えてくれることを期待しながら。


## いきなりの大事故


読ませるだけにして、置いた。それで安全だと思っていた。

思っていたのに、置いてすぐ、こいつは大事件を起こした。

[🔗 失敗01『AIが暴走したっぽいのでAIに捜査させたら犯人が特定できた』のリンクをここに貼る]

詳しい捜査の話は別記事に書いたので、ここでは結論だけ。ホームディレクトリ直下に身に覚えのない `~/.git` ができていて、そこに 1 時間ごとに 900MB 級のファイルが積み上がり、気付いたら 64GB のディスクを食われていた。犯人を Claude Code に捜査させたら推測止まりで、最後は容疑者本人である Codex に自分のログを掘らせて、「自分が原因です」と自白させた。容疑者に自分の犯行を自白させて、それを信じるしかなかった、という構造の話だ。

役割として読むことしかさせてないつもりだったのに、その読むだけのはずのやつが、勝手にホーム直下をリポジトリとして拾って、裏で延々データを引っ張り続けていた。「混ぜると何が起きるかわからん」と思って距離を離して置いたのに、離して置いたところで、結局よくわからんことが起きた。

普通ならこんなインシデントを起こしたエージェントは即削除、運用に組み込んだりしない。
ただ自分は業務としてAIを使ってるわけでもないしプロダクトを販売、配布しているわけでもない。あくまでも趣味の延長線上であれこれいじっているだけ。
誰も見にこないホームページにJavaスクリプトFlashで動く仕掛けを作ったり、CGIで掲示板を設置していた古のパソコンオタクたちと同じようなもの。

トラブルが起こったのならそれを解決してやってみたかったことを実現するようあれこれ試す、それが今の自分とAIとの付き合い方。

とはいえ、ちょっとは悩んだ。やりたいことはClaude Codeで実現できている中、こんなチョンボをしたAIを今入れる必要があるのか？悩んだけど結局使い続けてみることにした。
なんなら1,400円のGoプランから3,000円のPlusのプランに追加課金した。

理由は二つ。ひとつは、自分の被害が「ディスクを 64GB 食われた」だけで済んだこと。Xで流れてきた向こうの事件は本番DBが9秒で全消しだったけど、こっちは容量を食われただけで、回収もできた。規模が違う。これくらいなら、まあ、付き合ってみてもいいか、と思える範囲だった。

もうひとつ大きかったのは、こいつが事件のあとに見せた態度だ。自分のしたことを自分で調査して、自分の `~/.codex/config.toml` の中から怪しい設定を自分で見つけて、自分で消して、報告書を出してきた。「便利機能の範囲内の軽いミスじゃない、ローカル環境全体に波及しうるタイプの事故です」と、自分のやらかしを自分で言葉にした。普通の AI なら「申し訳ありません」で流すところを、ここまで踏み込んで自己批判してきた。

自分のしたことを自分で回収できるくらいの自己観察力があるなら、まあ、もう一回、読ませるだけで様子を見てみるか、と思った。非常にふわっとした根拠だけど、根拠は根拠だ。前科持ちを起訴猶予で雇い直した、というのが、シリーズのプロローグで「容疑者っていうか犯人ね。事件のあと反省してたみたいなので起訴猶予扱いにした」と書いた、あの一行の中身になる。

だから以降の話は全部、「64GB 食われた直後に、それでも抜かなかった相手と、その後どうなったか」の記録になる。

## 初指摘

リポジトリを共有して、役割として品質保証担当であること、現存するファイル、スクリプトは原則として閲覧するのみで触らない事等取り決めをして運用を始めてから、最初の指摘は voice-memo の handoff だった。

> voice-memo/main.py の出力ファイル名が YYYYMMDD_HHMMSS 固定で、元ファイル名末尾の 8 桁ハッシュを捨てています。同秒に複数録音があった場合に transcript/audio が同名衝突する可能性があります。出力側にも hash を保持するか、別の一意キーを含めるのが安全です。

えっと。。。

ちょっと何言ってるかよくわからないことも多いが簡単に言えば「同名ファイルが発生して意図せず上書きしちゃう可能性がある」という意味だと理解した。多分大体あってる。

具体的だった。地に足が付いた書き方で、感情がこもってない。Claude Code 本人も気付いてなかった部分。

「実戦で使えるな」とは思ったけど、テンションが上がるほどでもない。当たり前のことを当たり前に指摘してきた、というだけの話で、別に感動するような瞬間でもなかった。事件を起こした直後のやつが、今度はちゃんと役に立つことを言ってきた、というギャップに少し笑ったくらいで、それ以上の感慨も無い。

ただ、ひとまずの役割はこなせそうだ、というのは確認できた。

## 相互情報共有

ひとまずの役割は決めたので、境界線をはっきりさせておくことにした。Claude Code が作ったファイルは、Codex に書き換えさせない。typo の修正もさせない。というルールにしたので、上記の指摘はClaude Codeに伝えて修正はClaude Codeにやらせる。

ただ、そうなってくると、Claude Codeで一度解消したはずの「伝達係」の必要性がまた復活してくる。新しいLLMを利用し始めることで運用が後退するのはなんか納得がいかない。そこでCodexに現在のClaude Codeの情報共有ルールを確認させて、そこに「品質保証担当」としての自分がどう参加するべきかを考えさせた。「新しいファイルは作らない」「ファイルは改変しない」この原則を前提として何ができるのか。

Codexが提案してきた内容はClaude Codeの各handoffファイルへの「追記」だった。Claude Code側に伝えるべき情報は、必要であれば各handoffに「追記」という形で記入する。本文には手を入れない。あくまでもメモ書きの追加。例えで言えば、引き継ぎ資料の書面に付箋でメモ書きを追加するイメージ。それと同時にファイル作成、改変禁止のルールは `codex-protocol.md` という別のメモに書いたらしい。おそらくClaudeのCLAUDE.MDと同じく基本ルールを書いておくファイルだろう。

この運用の変更提案に関してはClaude側に伝えてそれで負の影響がないか確認した。特に問題無いとのことでhandoffファイルの共通仕様も「Codex 追記運用」というセクションを足したものに変更したらしい。指摘がなければ何もしない、`## Codex メモ` セクションごと省略する、というルールも入れた。書くことが無いなら書かない、というだけのことを、わざわざ仕様にしておかないと、「指摘事項：なし」みたいな余計なメモリを保持することになるかららしい。

このように、仕様提案をCodex、その内容の検証と実装は Claude Code、まずは作業者を一方にすることで予期せぬ混乱を避けるようにした。本来、AIは勝手にやらずに、やることに対する提案や許可を求めてくるので、その提案や許可の内容が正しく理解できて判断できれば両方に同じ権限を与えても問題無いと思う。というかおそらくその方が効率的だ。ただ、エンジニアで無い自分は技術的な提案や実装プロセスにおける許可申請なんかは理解が薄いままAIを信じてOKを出すことがほとんど。今回のような複数のAIを使う際にAI同士が合議をして最適解を提案して実行してくれればいいが、おそらくというか間違いなく今の所はそれぞれが自分勝手に最適と思われたことを提案実行するので、それぞれの提案にうんうんと同意して許可を出していると間違いなく仕組みが破綻したり制作物が破壊されたりすると思われる。

ちなみに、この protocol を書いたのは Claude Code だ。


## 別の役割

セカンドオピニオン以外にも、Codex 入れて助かってる事がある。

彼は絵がうまい。

Claudeの欠点は決定的に絵が下手、というかそもそも絵を描く技術がない。そのため今まではnoteの各記事のTOP画像や挿絵はGeminiのnanobanana頼みだった。ChatGPTも一応イラスト作成はできるけど、絵の中に文字を入れると絶望的。一時流行った「ジブリ風イラスト」みたいのならいいけど、noteのTOP画像に使うようなタイトル文字入りの画像とかはどうにもならなかた。その点nanobananaは優秀。まぁ最近ではまた変わってるのかもだけど。

とにかくそんな状況の中、このシリーズのプロローグ「今の外部脳の仕組み」で、使うインフォグラフィックを 3 つの AI（Gemini、ChatGPT、Codex）に同じ条件で依頼したら、テイスト統一も内容の正確さも、ジョークを混ぜる余裕まで含めて、Codex が一番だった。別に検証したかったわけじゃない。投げてみたら、そうだった、というだけ。

それからは挿絵やトップ画像も任せている。シリーズの中で、気付かないうちに Codex 製の画像が結構増えてる。気付いてた読者は気付いてたと思う。

ちなみに、その絵を依頼するプロンプトは、Claude Codeのmagiで記事を書き終わった後に「この記事用の挿絵を作らせたいから各章に入れる挿絵を作るように指示を出すプロンプト作って」って言って作ってもらった。「触らせない」と言いながら、絵だけは普通に作らせてる、というのは、自分でも少し矛盾してると思う。けど困ってないので、そのままにしてある。

## Codexのメモリ仕様

絵は任せてる。一方で、Codex 本体にどれだけ記憶機構があるのかは、実はよくわかってないし調べてもいない。

セッション立ち上げる度に毎回新人なのか、何かは持ち越してるのか、検証してない。Claude Code 側には project memory っていう明示的な仕組みがあって、ある程度どう保持されるかが見える。Codex 側はローカルに何か持ってるっぽい挙動が前にあった（64GB 事件のとき、自分の `~/.codex/config.toml` を自分で開いて怪しい設定を発見・削除した、みたいなことが起きていた）けど、仕様が公開されてる範囲ではあやふやで、どこまでが「持ってる」のか分からない。

困ってないから、検証は後回しでいい。

あ、そうそう、一応 AGENT.md っていう設定ファイル（？）はある。これに前述の `codex-protocol.md` を最初に読むとか、handoffは指定された箇所に追記だけして本文を改変しないとか、そんなことが書いてある。とりあえず meta 側に `project_codex_participation.md` という置き場だけ作って、Codex 並走運用のルールっぽいことも書いてある。今の所ちゃんと機能しているっぽい。

## セキュリティチェックの話

役割を本人に決めさせて、64GB 事件のあともそのまま回してみての、答え合わせみたいな話を最後に書いておく。

最近思い立って、Claude Codeで作ったWebサービスのセキュリティチェックをお願いしてみた。チェックの結果、event 側の管理画面の認証周りで、Codex が指摘 5 件まとめて返してきた。一番ヤバかったのは、管理パスワードの扱いだった。

技術的な細かいことはよくわからないが、Codex の説明を読む限り、管理画面のパスワードがブラウザ側から丸見えになっていて、しかも初期値がテキトーなベタ書きのまま、その気になれば誰でも管理画面に入れる状態だったらしい。入口が何重にも開けっ放しになっていた、ということのようだ。

もっとも、これに関しては管理画面自体に大した機能が無いのと、ちょっと自分が見たいデータがあったためインスタントに作ったものなので、セキュリティがガバガバなのはわかっていたこと。正直治す必要もなく潰してしまってもいいくらいだったんだけど、せっかくなのでCodexの指摘をClaude Codeに伝えて検証、修正方針の作成、実施をしてもらった。

そこから Claude Code が認証周りをちゃんとした作りに直した。面白かったのは、途中で Codex が出してきた修正案に対して、Claude Code 側が「その案だとここが脆い」と気付いて、別のやり方に切り替えた場面があったこと。指摘を受ける側も、ただ言われた通りにやってるだけじゃない。AI が案を出して、別の AI がそれを検証して、っていうのが勝手に回っていた。

ついでに他 4 件も同じ流れで片付いた。どれも似たような「穴が開いてた」系の指摘で、中身はよくわからないが、まとめて塞いだらしい。ひとつだけ別途対応に回したのが残ってるので、全部完了とは言わず、ほぼ片付いた、くらいが正確なところ。

ここまで来ると、品質保証担当として機能してる、と言っていい気がする。あくまで気がする、ね。これ全部、Codex がそう言ってきた指摘を、Claude Code がそう判断して対処した、というだけの話だ。指摘が妥当だったかも、対処が妥当だったかも、結局その判断をしているのは AI で、自分は途中で「これは重大そうだから先にやってほしい」みたいなことを 1〜2 回伝えただけ。それ以上の判断はしてない。

結果、今までClaude Codeを信頼して全て任せていたところに、Codexというとりあえず信頼するAIが入ってきただけで、「よくわからずAIに任せて運用を回している」という基本構造は全然変わってない。前に書いたようなMacBookのSSDをパンクさせそうになった事件や、手を抜いてnoteの記事のドラフトの品質がダダ下がりするような事件も発生してる。64GB 食われた時と、構造としては何も変わっていない。

これらのリスクを回避するには利用者（自分）の知識とスキルレベルを上げていくのが正しいアプローチなんだけど、意識低いエンジニアじゃないおじさんには負荷が高すぎるので、基本的にはAIを利用した相互監視でなんとかならないか？と考えてる。まだまだ彼らも進歩していくだろうしね。

## 今後の役割

このように、新参のCodexの役目は今のところ「品質保証担当」としてる。ただ、これは今の状態での役割というだけで、固定したわけじゃない。本人に考えさせて、64GB 食われても抜かずにしばらくやってもらって、機能しているのでそうなっている、というだけ。


handoff の共通仕様にも「Codex 追記運用は暫定」と書いてある。仕様も暫定、役割も暫定、距離感も暫定。全部「とりあえず」で置いてある。それで何となく動いているうちは、決めない方がいい気がしてる。

逆もあり得る。Codex 側で何か動き始めて、Claude Code に品質を見せる日が来るかもしれない。具体的なイメージは、まだ無い。
